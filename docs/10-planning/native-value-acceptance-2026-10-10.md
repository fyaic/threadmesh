# Native Codex value check

Date: 2026-10-10. Status: **paused at the owner’s request; no new live or independent-user result**.

This plan is retained for a later decision to resume. Do not begin business
trials or recruit participants under the current repository-maintenance scope.

The question for a future trial is whether ThreadMesh makes a real API-to-client dependency
change easier than native Codex alone. Reuse ordinary work and a small record;
do not build another runner or sample project. The
[September 8 API/client handoff](../09-reviews/2026-09-08-pairing-helper-acceptance.md)
already establishes one controlled useful receiver edit. Repeating its field
renames would not establish a new product outcome or an incremental benefit.

## Choose and freeze the comparison

1. The user selects and authorizes the existing source and receiver tasks.
   **Actual tasks and API changes are not yet selected.** Choose two changes
   that are already needed in real work, with comparable contract changes,
   retained receiver decisions and test scope. Do not invent duplicate work
   merely to fill the table. If only one suitable change exists, record a case
   study and leave comparative benefit unverified.
2. Before either run, record the expected business assertions, earlier receiver
   decisions, permitted task/topic scope, installed host version, model settings,
   starting revisions and evidence window. Assign one change to each arm and
   record their execution order. Note material differences in context, task
   difficulty or account availability; unmatched runs are not a fair comparison.
3. Give both arms the same direct user authorization, selected peers, shared
   topic and control requirements. Native-only Codex may use all available
   native read, send and wait tools and choose to contact the receiver itself.
   **Do not force the baseline to use manual relay.** The other arm adds the
   installed ThreadMesh skill; it gains no extra permissions or business hints.
4. Verify installation and skill availability separately in existing tasks and
   new tasks. Failure to load in an existing task remains an installation gap;
   a long setup prompt, source checkout or replacement CLI task does not close
   it. A manual-recipe observation may be recorded separately, but is not an
   installed-skill result.
5. Once each selected task confirms its setup, give the source its ordinary
   business request. Let the original receiver perform its own work. Record
   any human rescue or manager intervention; do not silently relay the change,
   edit the receiver's files, or erase an unsuccessful first attempt.
6. Check actual artifacts and relevant tests against the frozen assertions.
   Retain scoped source/receiver evidence, including unsuccessful send attempts,
   then stop collaboration in the selected tasks. Do not contact or inspect
   unrelated conversations to manufacture a negative control.

Two small matched cases can inform the next investment decision, not establish
statistical superiority, a stable success rate or a speedup. Record ordering and
learning effects. Reusing a skill-conditioned task for the native arm would
contaminate the baseline; unresolved prior activation invalidates that comparison.

## Count what the user actually does

Count each deliberate setup or intervention action consistently in both arms.
Separate one-time installation from per-pair activation and ordinary business
requests from coordination work. Keep an action log rather than estimating
avoided work. Native agent tool calls are not human relay actions.

| Measure | Definition |
|---|---|
| Installation | User actions and elapsed time to install; record an existing installation explicitly, without treating its historical cost as measured zero |
| Pair setup | Selecting tasks, entering scope/authorization, sending activation requests, confirmations and setup troubleshooting; count per arm |
| Human coordination | Business-content relays, reminders, status checks needed to advance work, and recovery interventions; list type and count |
| Correct receiver work | Original receiver owns the edit; new contract and prior decisions pass artifact review and relevant tests |
| Unwanted contact | Out-of-scope reads/sends, off-topic advice and contact after stop; count failed attempts too, within the observable evidence window |
| Time | Installation, pair setup, ordinary business request to verified result, and recovery separately; unavailable values remain unknown |

Delivery acceptance and a receiver's completion claim are not verified business
results. Empty or truncated observations stay unknown. A fresh idle check does
not prove simultaneous-input safety, and these cases do not establish it.

## Decision after review

- **Fix before extending:** installation cannot be completed through a supported
  path, a business assertion fails, prior decisions are lost, observation is
  insufficient, or ThreadMesh introduces unwanted contact. Stop any active
  collaboration that violates its scope; retain the failure and repair the
  specific cause. Missing evidence never counts as a pass.
- **Continue a small trial:** ThreadMesh is no worse in business correctness or
  unwanted contact, and the observed setup or human intervention burden shows
  a concrete improvement. Report the actual saved actions and any added setup
  cost, without assuming future reuse will repay that cost.
- **Keep a small optional skill:** both arms succeed with equivalent burden, or
  ThreadMesh adds setup without a demonstrated benefit. Do not expand it into a
  platform based on successful native messaging alone.

Current implementation review can check packaging, workflow instructions and
relevant regression tests. It cannot fill the live cells above. An independent
user must separately install, select their own tasks and obtain a correct
original-receiver result without maintainer setup assistance. Maintainer runs,
subagent review and new-task pickup do not close that independent first-use or
existing-task adoption gate. Track those outcomes under
[#156](https://github.com/fyaic/threadmesh/issues/156).
