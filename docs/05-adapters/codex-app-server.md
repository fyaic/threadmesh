# Codex App Server adapter experiment

> Experimental implementation note for Codex CLI `0.145.0`. This is not a
> production compatibility claim and does not claim parity with private Codex
> Desktop cross-task tools.

ThreadMesh now contains a conservative adapter for the documented Codex App
Server JSONL/JSON-RPC surface. It was implemented against both the official
documentation and the exact schemas generated by the installed CLI.

Primary reference: [official Codex App Server documentation](https://developers.openai.com/codex/app-server/).

## Implemented surface

- `initialize` followed by `initialized`;
- `thread/start`, `thread/resume`, and exact-target `thread/delete`;
- accepted suggestion admission through `turn/start`;
- bounded `item/agentMessage/delta` aggregation;
- exact `turn/completed` correlation by thread and turn ID;
- denial of every server-initiated approval, permission, elicitation, dynamic
  tool, and structured-input request;
- absolute command/cwd validation, a minimal environment allowlist, timeout
  termination, bounded stderr, and typed failure categories.

The adapter always starts or resumes the receiver with approval policy `never`
and sandbox mode `read-only`. This is an adapter default, not an operating-system
sandbox supplied by ThreadMesh.

## Capability claim

The published profile supports only `suggest` with receiver-mediated
`checkpoint-offer` delivery. It advertises explicit-only discovery,
model-visible provenance, checkpoint completion events, and no durable native
submission idempotency.

Although App Server documents `turn/steer` and `turn/interrupt`, this adapter
does not advertise either intent. API availability alone does not prove the
ThreadMesh requirements for restart-safe receipts, objective freshness,
partial cancellation coverage, and typed interruption results. Likewise,
`thread/inject_items` is not used: it writes model-visible history and is not a
receiver mailbox.

## Receiver admission and provenance

`runAcceptedSuggestion` rejects any request without a matching explicit
receiver decision of `accepted`. The accepted envelope is serialized as one
canonical JSON object beneath the marker
`THREADMESH_UNTRUSTED_PEER_CONTEXT_JSON_V1`. JSON escaping prevents peer content
from closing the wrapper or forging adjacent metadata.

This preserves visible semantic provenance, but App Server receives the object
as ordinary text input. The adapter cannot prove a provider-native role with
lower instruction precedence. Peer content is therefore still untrusted prompt
content, and structured approval or permission responses are never parsed from
it.

## Empty-thread persistence finding

The installed `0.145.0` product accepts `thread/start` without a model turn but
does not create a resumable rollout at that point. A subsequent `thread/resume`
returns `no rollout found for thread id`, even when attempted before any model
work. The adapter therefore makes two distinct claims:

- the default smoke test verifies initialize and empty read-only thread start;
- a persisted lifecycle is verified only after the optional live first turn,
  after which the script resumes and deletes that exact thread.

`startThreadWithAcceptedSuggestion` keeps start and the first accepted turn on
one App Server connection. `runAcceptedSuggestion` is reserved for a receiver
thread that already has durable product history.

## Run and evidence

```sh
npm test
npm run smoke:codex
```

The second command performs no model turn. It records the CLI version, digest
of generated protocol schemas, sanitized initialize snapshot, and empty-thread
start result. The gated live marker is:

```sh
npm run smoke:codex:live
```

Do not count the live command as passed unless the exact untruncated marker,
terminal turn, persisted resume, and exact-thread cleanup all pass. Current
evidence and the gate are recorded in the
[Codex preflight report](../09-reviews/2026-08-20-codex-app-server-preflight.md).

## Remaining boundaries

- Admission arguments are trusted-process evidence until wired to the merged
  coordinator claim/receipt state machine. The stacked multi-product candidate
  now supplies that wiring and deterministic evidence; merge remains gated.
- No OS container or process sandbox is supplied.
- The first real model marker and existing-receiver A-to-B scenario remain
  gated by M0 review and the M1 stack.
- App Server compatibility is pinned to `>=0.145 <0.146` until another generated
  schema and product run are recorded.
