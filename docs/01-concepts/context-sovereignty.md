# Context sovereignty

Context sovereignty is the receiver's right to control what enters its model-visible history, changes its objective, or interrupts its execution.

## Why it matters

Agent messages are not neutral data. Once inserted into a model conversation, they may:

- redirect attention away from the user's latest request;
- introduce stale assumptions;
- consume context and reduce recall quality;
- trigger tools or writes;
- appear indistinguishable from user-authored instructions;
- persist through summaries or compaction.

Therefore, delivery to a task mailbox and injection into model context are separate operations.

## Ownership hierarchy

The default authority order is:

```text
user owner > `supervisor` > `parent` > task itself > `child`/`peer`/`dependency` > `observer` > unrelated
```

This order does not automatically grant every higher principal every action. Policy and freshness still apply.

## Receiver choices

A receiver may:

- accept and inject the message at the next checkpoint;
- accept it as non-model-visible metadata;
- defer it until a named phase completes;
- reject it as irrelevant or unauthorized;
- mark it stale because the objective changed;
- request clarification from the sender;
- escalate it to the user.

## User-facing requirement

A UI should distinguish:

- user-authored instructions;
- messages generated by the current agent;
- messages sent by another task;
- policy or system events;
- accepted versus unaccepted suggestions.

The source label is not cosmetic. It preserves the user's ability to understand whose intention affected the task.
